## บทที่ 1: บทนำและสภาพแวดล้อมระบบ (Introduction & Scope)

### 1.1 วัตถุประสงค์ของเอกสาร (Purpose)
เอกสารข้อกำหนดความต้องการของซอฟต์แวร์ (SRS) ฉบับนี้ จัดทำขึ้นภายใต้กระบวนการวิศวกรรมซอฟต์แวร์ **ISO/IEC 29110 (Software Implementation Process: SI.2 Requirements Analysis)** และมาตรฐาน **IEEE Std 830-1998** เพื่อกำหนดขอบเขตหน้าที่ ฟังก์ชันการทำงาน และเกณฑ์การยอมรับ (Acceptance Criteria) ของ **"ระบบติดตามและแจ้งเตือนพัสดุหอพัก (RMUTL Smart Dormitory Package Notification & Tracking System)"** อย่างเป็นทางการ โดยรวบรวมข้อมูลจากการสัมภาษณ์ **อาจารย์ชุณ (นางสาวชุณหะกาญจน์ พันธุ์เจริญ)** ในฐานะตัวแทนผู้ว่าจ้างและผู้ใช้งานหอพัก เพื่อใช้เป็นข้อตกลงตั้งต้น (Approved Baseline) สำหรับส่งมอบให้ทีมพัฒนานำไปออกแบบสถาปัตยกรรม (SI.3) และพัฒนาโปรแกรม (SI.4) ต่อไป

### 1.2 ขอบเขตของระบบ (System Scope)
ระบบครอบคลุมกระบวนการจัดการพัสดุหอพักแบบครบวงจร 5 มิติหลัก:
1. **การบันทึกและตรวจสอบชื่อผู้รับ (Exact Match Verification):** ตรวจสอบชื่อ-นามสกุลบนกล่องพัสดุเทียบกับฐานข้อมูลนักศึกษา เพื่อกรอกข้อมูลห้องพักและ LINE ID ให้อัตโนมัติ
2. **ระบบจำลองการแจ้งเตือนส่วนบุคคล (Personal Notification Mockup):** จำลองการส่ง LINE Notify ตรงถึงนักศึกษาทันทีที่พัสดุเข้าระบบ
3. **ระบบจำลองการแจ้งเตือนซ้ำ (Overdue Reminder Mockup):** ตรวจสอบพัสดุที่ค้างรับเกินกว่า 5 ชั่วโมง และส่งข้อความเตือนเร่งรัดให้นักศึกษามารับของ
4. **กระดานประกาศพัสดุไม่ทราบชื่อและระบบเคลม (Broadcast Board & Claim):** นำพัสดุที่อ่านชื่อไม่ออกหรือไม่พบในระบบขึ้นประกาศบนกระดานกลาง และเปิดให้นักศึกษายื่นขอเคลมสิทธิ์
5. **หน้าจอลงนามและเซ็นรับพัสดุดิจิทัล (Digital Signature Canvas):** นักศึกษาลงลายมือชื่อผ่านหน้าจอเพื่อยืนยันการรับพัสดุ พร้อมประทับเวลาจริงและเก็บหลักฐานในฐานข้อมูล

### 1.3 นิยาม คำศัพท์ และคำย่อ (Definitions & Acronyms)
* **SRS:** Software Requirements Specification (เอกสารข้อกำหนดความต้องการของซอฟต์แวร์)
* **FR / NFR:** Functional Requirement (ความต้องการเชิงหน้าที่) / Non-Functional Requirement (ความต้องการเชิงคุณภาพ)
* **VSE:** Very Small Entity (องค์กรหรือทีมพัฒนาขนาดเล็กที่มีบุคลากรไม่เกิน 25 คน ตาม ISO/IEC 29110)
* **Exact Match Verification:** การเปรียบเทียบชื่อ-นามสกุลภาษาไทยระหว่างหน้ากล่องกับฐานข้อมูลนักศึกษาแบบตรงกันทุกตัวอักษร
* **Digital Signature:** ลายมือชื่อดิจิทัลที่นักศึกษาวาดลงบนผืนผ้าใบ Canvas และถูกแปลงเป็น Base64 Data URL เพื่อเก็บเป็นหลักฐาน
* **Broadcast Board:** กระดานกลางที่รวบรวมพัสดุไม่ทราบชื่อ เพื่อให้นักศึกษาเข้ามาตรวจสอบภาพถ่ายและยื่นเคลม

## บทที่ 2: ภาพรวมของระบบและลำดับความสำคัญ (Overall Description & MoSCoW)

### 2.1 มุมมองของระบบ (System Perspective)
ระบบทำงานบนสถาปัตยกรรมแบบ **Multi-tier Client-Server with Layered Architecture**:
* **Client Tier:** Staff Portal (`:5174`) สำหรับเจ้าหน้าที่ และ Student Portal (`:5173`) สำหรับนักศึกษา (Responsive)
* **Server Tier:** Node.js + Express.js API (`:5000`) ทำหน้าที่ประมวลผล Business Logic, ระบบแจ้งเตือน และ Centralized Error Handling
* **Database Tier:** MongoDB (`:27017`) จัดเก็บข้อมูลนักศึกษา (students), พัสดุ (packages) และประวัติการแจ้งเตือน (notifications)

## บทที่ 3: ข้อกำหนดความต้องการเชิงหน้าที่และเกณฑ์การยอมรับ (Functional Requirements & Acceptance Criteria)

### 📌 REQ-FR01: การบันทึกพัสดุและการตรวจสอบชื่อนักศึกษา (Exact Match Verification)
* **ความสำคัญ:** **Must Have (จำเป็นวิกฤต)**
* **ผู้ใช้งานหลัก:** เจ้าหน้าที่หอพัก (Staff Portal :5174)
* **คำอธิบาย:** ระบบต้องสามารถให้เจ้าหน้าที่กรอกชื่อ-นามสกุลผู้รับที่พบบนกล่องพัสดุ และทำการเปรียบเทียบกับฐานข้อมูลทะเบียนนักศึกษาของหอพักแบบตรงกันทุกตัวอักษร (Exact Match)
* **ข้อมูลนำเข้า (Inputs):** `tracking_number` (String, จำเป็น), `receiver_name_on_box` (String, จำเป็น), `image_path` (String, ทางเลือก - รูปถ่ายกล่องพัสดุ)
* **ขั้นตอนการทำงาน (Workflow):**
  1. เจ้าหน้าที่กรอกชื่อผู้รับลงในแบบฟอร์มบันทึกพัสดุ
  2. ระบบค้นหาชื่อในฐานข้อมูลนักศึกษาแบบ Exact Match ทันที (ตัดช่องว่างหน้า-หลัง)
  3. **กรณีพบชื่อ (Matched):** ระบบแสดงข้อความและไอคอนสีเขียว ทำการ Auto-fill ข้อมูลห้อง อาคาร และ LINE ID ให้อัตโนมัติ
  4. **กรณีไม่พบชื่อ (Unmatched):** แสดงข้อความเตือนสีส้ม และแนะนำให้จัดพัสดุเข้าหมวด "unknown" (พัสดุไม่ทราบชื่อ)
  5. เจ้าหน้าที่กดยืนยันบันทึก -> ข้อมูลถูกจัดเก็บลงฐานข้อมูล MongoDB
* **เกณฑ์การยอมรับความต้องการ (Acceptance Criteria):**
  * `AC-1.1:` ระบบต้องตรวจสอบชื่อตรงกับฐานข้อมูลแบบ Exact Match 100% (ตรงทั้งชื่อและนามสกุล)
  * `AC-1.2:` เมื่อตรวจสอบพบชื่อ ต้องทำ Auto-fill ข้อมูลห้อง อาคาร และ LINE ID โดยเจ้าหน้าที่ไม่ต้องพิมพ์เอง
  * `AC-1.3:` เมื่อชื่อไม่ตรง ต้องไม่อนุญาตให้เลือกสถานะ pending โดยบังคับจัดเข้าหมวด unknown
  * `AC-1.4:` ต้องมี Form Validation ป้องกันการส่งข้อมูลว่าง (แสดงข้อความแจ้งเตือนสีแดงหากไม่กรอกชื่อหรือเลขพัสดุ)

### 📌 REQ-FR02: ระบบจำลองการแจ้งเตือนส่วนบุคคลทันที (Personal Notification Mockup)
* **ความสำคัญ:** **Must Have (จำเป็นวิกฤต)**
* **ผู้ใช้งานหลัก:** ระบบอัตโนมัติ (Server Daemon) / นักศึกษาเจ้าของพัสดุ
* **คำอธิบาย:** เมื่อเจ้าหน้าที่บันทึกพัสดุที่จับคู่นักศึกษาสำเร็จ ระบบจะต้องจำลองการส่งข้อความแจ้งเตือนส่วนบุคคล (Mock LINE Notify) ไปยัง LINE ของนักศึกษาทันทีในระดับมิลลิวินาที
* **ข้อมูลนำเข้า (Inputs):** ข้อมูลพัสดุที่บันทึกสำเร็จ, รหัสนักศึกษา และ LINE User ID ของผู้รับ
* **ขั้นตอนการทำงาน (Workflow):**
  1. ทันทีที่บันทึกพัสดุสำเร็จ (`POST /api/packages`) หากมีนักศึกษาที่จับคู่ได้
  2. ระบบเรียกใช้ Notification Service ส่งข้อความแจ้งเตือนจำลองผ่าน Server Logger ทันที
  3. บันทึกประวัติการส่งลงใน Collection `notifications` (ประเภท: `arrival`)
  4. หากเป็นพัสดุไม่ทราบชื่อ (Unknown) ระบบต้องไม่ส่งแจ้งเตือนรบกวนนักศึกษาคนใด
* **เกณฑ์การยอมรับความต้องการ (Acceptance Criteria):**
  * `AC-2.1:` ระบบต้องส่งแจ้งเตือนจำลองได้ภายในเวลาไม่เกิน 1 นาทีหลังกดบันทึก (เกณฑ์เป้าหมาย < 3 วินาที)
  * `AC-2.2:` เนื้อหาข้อความต้องครบถ้วน 5 องค์ประกอบ: 1) ชื่อ-สกุล 2) ห้อง/ตึก 3) เลขพัสดุ 4) วันเวลาพัสดุเข้า 5) คำแนะนำการนำหลักฐานมารับ
  * `AC-2.3:` พัสดุสถานะ unknown ต้องไม่กระตุ้นการส่ง Mock LINE Notify รายบุคคลเด็ดขาด

### 📌 REQ-FR03: ระบบจำลองการแจ้งเตือนซ้ำพัสดุค้างรับเกิน 5 ชั่วโมง (Overdue Reminder Mockup)
* **ความสำคัญ:** **Should Have (สำคัญสูง)**
* **ผู้ใช้งานหลัก:** ระบบอัตโนมัติ (Background / Reminder Scanner)
* **คำอธิบาย:** ระบบต้องสามารถสแกนค้นหาพัสดุที่ถูกบันทึกเข้าระบบมาแล้วเกินกว่า 5 ชั่วโมง และยังคงมีสถานะ "pending" เพื่อส่งข้อความจำลองแจ้งเตือนซ้ำเร่งรัดให้นักศึกษามารับของ
* **ข้อมูลนำเข้า (Inputs):** เกณฑ์ชั่วโมงค้างรับ (`hours=5`) ผ่าน Endpoint `GET/POST /api/notifications/check-reminders`
* **ขั้นตอนการทำงาน (Workflow):**
  1. ระบบสแกนหาพัสดุที่ `arrival_date` ผ่านมาเกินกว่า 5 ชั่วโมง และ status เป็น 'pending'
  2. ระบบสร้างข้อความแจ้งเตือนซ้ำระบุจำนวนชั่วโมงที่ค้างรับจริง และส่งตรงถึง LINE ของนักศึกษา
  3. บันทึกเวลาที่ส่งเตือนซ้ำ (`reminded_at`) และประวัติในฐานข้อมูล
  4. พัสดุที่ถูกเซ็นรับไปแล้ว (`status: 'received'`) จะต้องไม่ถูกนำมาแจ้งเตือนซ้ำเด็ดขาด
* **เกณฑ์การยอมรับความต้องการ (Acceptance Criteria):**
  * `AC-3.1:` ระบบต้องตรวจจับพัสดุค้างรับเกิน 5 ชั่วโมงได้อย่างแม่นยำตามเวลาจริง
  * `AC-3.2:` ข้อความเตือนซ้ำต้องระบุหัวข้อชัดเจนว่าเป็น '⏰ แจ้งเตือนซ้ำ: พัสดุยังไม่ถูกรับเกิน 5 ชั่วโมง' พร้อมเตือนให้ติดต่อห้องธุรการ
  * `AC-3.3:` พัสดุที่รับแล้ว (received) แม้บันทึกเกิน 5 ชม. ต้องได้รับการยกเว้นจากการแจ้งเตือน 100%

### 📌 REQ-FR04: กระดานประกาศพัสดุไม่ทราบชื่อและระบบยื่นเคลม (Broadcast Board & Claim)
* **ความสำคัญ:** **Must Have (จำเป็นวิกฤต)**
* **ผู้ใช้งานหลัก:** เจ้าหน้าที่หอพัก (สั่ง Broadcast) และ นักศึกษา (ดูบอร์ดและเคลม)
* **คำอธิบาย:** เจ้าหน้าที่สามารถกดส่งพัสดุไม่ทราบชื่อขึ้นกระดานบอร์ดกลาง และนักศึกษาสามารถเปิดดูภาพถ่าย วันเวลา และกดยื่นคำร้องขอเคลมพัสดุว่าเป็นของตนเองได้
* **ข้อมูลนำเข้า (Inputs):** คำสั่ง Broadcast จากเจ้าหน้าที่, ข้อมูลยืนยันตัวตนและหลักฐานการเคลมจากนักศึกษา
* **ขั้นตอนการทำงาน (Workflow):**
  1. เจ้าหน้าที่เลือกพัสดุไม่ทราบชื่อและกดปุ่ม 'ประกาศขึ้นบอร์ด (Broadcast)'
  2. พัสดุแสดงผลเป็นการ์ดบนหน้าจอ Broadcast Board ของ Student Portal ทันที
  3. นักศึกษาตรวจสอบภาพถ่ายและกดปุ่ม 'นี่คือพัสดุของฉัน (เคลม)'
  4. นักศึกษากรอกข้อมูลชื่อ รหัส และหลักฐานยืนยัน -> กดยืนยันการเคลม
  5. ระบบผูกพัสดุเข้ากับนักศึกษา ย้ายเข้าสู่รายการรอรับของนักศึกษา และลดจำนวน Unknown ในฝั่งเจ้าหน้าที่ทันที
* **เกณฑ์การยอมรับความต้องการ (Acceptance Criteria):**
  * `AC-4.1:` เมื่อกด Broadcast ข้อมูลต้องปรากฏบนบอร์ดกลางของ Student Portal ทันที
  * `AC-4.2:` การ์ดพัสดุบนบอร์ดต้องแสดงรูปถ่าย วันเวลา เลขพัสดุ และปุ่มเคลมอย่างชัดเจน
  * `AC-4.3:` เมื่อนักศึกษายื่นเคลมสำเร็จ ระบบต้องย้ายพัสดุเข้าสู่รายการรอรับของนักศึกษาทันที
  * `AC-4.4:` ข้อมูลการเคลมต้องสะท้อนกลับมายังหน้าจอ Staff Portal แบบ Real-time ตรงกันทั้งสองฝั่ง

### 📌 REQ-FR05: หน้าจอลงนามและเซ็นรับพัสดุดิจิทัล (Digital Signature Canvas)
* **ความสำคัญ:** **Must Have (จำเป็นวิกฤต)**
* **ผู้ใช้งานหลัก:** นักศึกษาผู้รับพัสดุ และ เจ้าหน้าที่ผู้ส่งมอบ
* **คำอธิบาย:** นักศึกษาจะต้องลงลายมือชื่อดิจิทัลผ่านผืนผ้าใบ Canvas บนหน้าจอ เพื่อยืนยันการรับพัสดุ โดยระบบจะแปลงลายเซ็นเป็น Base64 บันทึกเก็บเป็นหลักฐานพร้อมประทับเวลาจริง
* **ข้อมูลนำเข้า (Inputs):** ภาพวาดลายมือชื่อดิจิทัล (Base64 PNG Data URL), รหัสนักศึกษา
* **ขั้นตอนการทำงาน (Workflow):**
  1. นักศึกษาค้นหารายการพัสดุของตนเองใน Student Portal และกดปุ่ม 'เซ็นรับพัสดุ'
  2. หน้าต่าง Modal แสดงกระดานวาดลายมือชื่อ (Canvas) ขึ้นมา รองรับทั้งเมาส์และทัชสกรีน
  3. นักศึกษาวาดลายมือชื่อ (มีปุ่ม Clear สำหรับล้างลายเซ็นวาดใหม่)
  4. นักศึกษากดปุ่ม 'ยืนยันการรับพัสดุ' -> ระบบส่งลายเซ็นไปบันทึกลงฐานข้อมูล
  5. สถานะพัสดุเปลี่ยนจาก 'pending' เป็น 'received' พร้อมบันทึกวันเวลารับมอบ (`pickup_date`)
* **เกณฑ์การยอมรับความต้องการ (Acceptance Criteria):**
  * `AC-5.1:` กระดานลายมือชื่อต้องวาดเส้นได้ลื่นไหล คมชัด ไม่หน่วง และปุ่มล้างลายเซ็นต้องรีเซ็ตผ้าใบได้สะอาด
  * `AC-5.2:` ต้องมี Form Validation บล็อกไม่ให้กดยืนยันหากยังไม่ลงลายมือชื่อ (Empty Canvas)
  * `AC-5.3:` เมื่อยืนยันสำเร็จ สถานะพัสดุต้องเปลี่ยนเป็น received และประทับเวลา pickup_date ปัจจุบันทันที
  * `AC-5.4:` ภาพลายเซ็นต้องถูกจัดเก็บอย่างปลอดภัยในฐานข้อมูลและเรียกดูย้อนหลังเป็นหลักฐานได้
